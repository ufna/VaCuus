# Task B — Scene backdrop-filter (LDR glass): OutputTexture-copy design verified against 5.8.1

**Verdict:** the OutputTexture-copy mechanism is correct for LDR game and PIE in 5.8.1 and remains the right choice (Slate post buffers remain unreachable: `FDrawPassInputs` carries only the `ESlatePostRT UsedSlatePostBuffers` flag field, no texture — `Runtime/SlateCore/Public/Rendering/RenderingCommon.h:951`). Four corrections to the spec's picture, in severity order:

1. **The spec's implicit "bake glass at replay time" collides with the M2 idle gate** — a static HUD stops publishing, replay stops running, and the baked blurred scene freezes while the live scene moves. Glass must be composited **per engine frame** in the Slate element, not baked into the per-view RT. This is the design correction that changes the shape of the work (§5 below).
2. **The literal copy is avoidable** — the engine's own Slate blur samples the very same `OutputTexture` directly as an SRV mid-frame; the "copy" and the half-res downsample collapse into one pass (§2).
3. **"The M1 spike ported RmlUi's GL3 blur chain" is false.** The tree contains exactly one shader file, `VaCuusUI.usf`; the blur chain exists only as vendored GL3 *reference source* and as spec future-work text (§3). The port is still unbuilt.
4. **In HDR-composite mode the custom element's OutputTexture contains no scene at all** — glass is structurally LDR-only, and detecting the HDR mode from inside `Draw_RenderThread` is unreliable (§1, §6, Exp-4).

---

## 1. What `FDrawPassInputs::OutputTexture` IS at Draw_RenderThread time

The struct (`Runtime/SlateCore/Public/Rendering/RenderingCommon.h:945-954`): `FRDGTexture* OutputTexture`, `FIntRect SceneViewRect`, `ElementsMatrix`, `ElementsOffset`, `HDRDisplayColorGamut`, `UsedSlatePostBuffers`, `bOutputIsHDRDisplay`, `bWireFrame`. **No scene-texture member.**

The invocation (`Runtime/SlateRHIRenderer/Private/SlateRHIRenderingPolicy.cpp:1689-1707`): the CustomDrawer batch case sets `DrawInputs.OutputTexture = ElementsTexture.Texture` (:1700), where `ElementsTexture` is `FScreenPassTexture(Inputs.ElementsTexture)` (:1506). So OutputTexture ≡ the **elements texture**, which `FSlateRHIRenderer::DrawWindowViewport_RenderThread` wires as follows (`SlateRHIRenderer.cpp`):

- `*OutputTextureRHI = bCompositeStereoToSwapChain ? *ViewportTextureRHI : SwapChainTextureRHI` (:972) — the window backbuffer in the non-stereo case — registered as RDG external texture `"SlateOutputTexture"` (:984).
- `FRDGTexture* ElementsTexture = OutputTexture` (:987) — **except** when `bCompositeUIWithSceneHDR`, which allocates a *separate*, cleared-to-transparent UI texture (`CompositeUIWithSceneHDRTexture`, :999-1013). In that mode the custom element draws into a UI-only texture and the scene never passes through it; the scene meets the UI later in the `CompositeUI` CS/PS pass (:1080-1147).

**What is in it before we draw:**

- **-game, LDR (direct rendering):** `UGameEngine` creates the game `SViewport` with `.RenderDirectlyToWindow(bRenderDirectlyToWindow)` (true absent movie capture — `Runtime/Engine/Private/GameEngine.cpp:215-222`), so `FSceneViewport::bUseSeparateRenderTarget = !ShouldRenderDirectly() = false` (`Runtime/Engine/Private/Slate/SceneViewport.cpp:76`) and the scene renderer's target is set to the window's backbuffer (`ViewportProvider->GetBackBufferResource()`, SceneViewport.cpp:2285-2303). [inference: the scene render is enqueued from the engine's viewport draw earlier in the frame than Slate's window draw, so the backbuffer physically holds the tonemapped scene when the Slate graph executes — this ordering is standard but I did not trace the tick order; Exp-1 settles it by observation.] Slate then draws **over** it: `ElementsLoadAction = ELoad` because `bClear` is only true for per-pixel-transparent windows (`SlateRHIRenderer.cpp:1737`, consumed at :992, :1072). With direct rendering the viewport widget adds **no** quad (`SViewport::OnPaint` draws `MakeViewport` only `if (!ShouldRenderDirectly())` — `Runtime/Slate/Private/Widgets/SViewport.cpp:165-169`).
- **PIE / editor:** the viewport uses a separate RT (SceneViewport.cpp:76; editor viewports never render directly), allocated at `r.DefaultBackBufferPixelFormat` (SceneViewport.cpp:2391-2465) — CVar default **4 → `PF_A2B10G10R10`** (`Runtime/Renderer/Private/SceneTextures.cpp:71-80`; mapping `Runtime/Engine/Private/RendererSettings.cpp:41-43`). That RT is drawn into the editor window's backbuffer as an ordinary **primitive** Slate batch (`MakeViewport` → `FSlateElementBatcher::AddViewportElement` → `CreateRenderBatch(... ESlateShader::Default ...)`, `Runtime/SlateCore/Private/Rendering/ElementBatcher.cpp:2709-2740`) at the viewport widget's layer. The batch loop **flushes all accumulated primitive passes before running a custom drawer** (`SlateRHIRenderingPolicy.cpp:1678-1682`, then the CustomDrawer case at :1689). [inference: RDG executes raster passes on the graphics pipe in submission order, so those flushed passes have written the scene quad into OutputTexture by the time our passes execute — consistent with the engine relying on the same ordering for its own blur batch at :1712-1745.]

So the spec's claim ("at Slate custom-element time the output texture already contains the tonemapped scene", spec :193-196) is **verified for LDR game and PIE**, with the content **display-encoded** (gamma) LDR, default format `PF_A2B10G10R10` (note: 2-bit alpha — never rely on destination alpha) or `PF_B8G8R8A8`. Bonus: `SceneViewRect` is populated from the window's `ViewportRect` (`SlateRHIRenderer.cpp:1728` → :1034) — use it to clamp the blur-source region in PIE.

**HDR caveat:** under an HDR display the window format is `GRHIHDRDisplayOutputFormat` (`SlateRHIRenderer.cpp:760-766`) and `bCompositeUIWithSceneHDR` decouples the elements texture — glass sees a transparent UI-only texture. Worse, the SDR elements pass in that mode runs with `bElementsTextureIsHDRDisplay = false` (set at :1069 after the HDR batch), so `Inputs.bOutputIsHDRDisplay` **cannot** detect the situation (Exp-4).

## 2. The copy: RDG-legal, and avoidable

- A literal `AddCopyTexturePass(GraphBuilder, OutputTexture, Transient)` is engine-precedented on the identical texture (`SlateRHIRenderer.cpp:1140-1147`, the `CompositeUI` PS fallback).
- **It is avoidable.** The engine's own background blur samples the same texture directly: the PostProcess batch sets `BlurInputs.InputTexture = Inputs.SceneViewportTexture` — which in LDR *is* `OutputTexture` (`SceneViewportTexture = OutputTexture` at `SlateRHIRenderer.cpp:1032`; `ElementsTexture == OutputTexture` at :987) — see `SlateRHIRenderingPolicy.cpp:1718-1727, 1738`; the downsample and blur passes then bind it as an SRV through RDG parameter structs (`SlatePostProcessor.cpp:784-792` downsample; `:717-720` blur `ElementTexture`), writing the result back into the same OutputTexture (:822-832). RDG inserts the RTV↔SRV transitions between passes. Therefore: **one `AddDrawScreenPass` that samples OutputTexture's DestRect bilinearly into a half-res target is simultaneously the copy and the downsample.** The only hard rule is never sampling OutputTexture in the same pass that renders to it — our glass draw binds OutputTexture as RT and samples only the blurred RT, so it's clean.
- Residual platform risk: in -game the "texture" is a swapchain image; the engine path above implies swapchain-as-SRV works on supported RHIs, but verify once on our Linux/Vulkan (Exp-2); fallback is the 1147-style copy.
- If the blurred texture must ever be read inside the **raw-RHI replay lambda** (design B below), it must be handed in via the *parameter-struct* `AddPass` overload so RDG performs the transition (`Runtime/RenderCore/Public/RenderGraphBuilder.h:203-221`); the current replay pass is the parameterless overload that forbids accessing non-external RDG resources (`RenderGraphBuilder.h:227-231`; used at `VaCuusSlateElement.cpp:70`).

## 3. The blur: what the plugin actually has — nothing

Shipped shader inventory is exactly `Shaders/Private/VaCuusUI.usf` (`MainVS`/`MainPS`/`MainCompositePS`, :8-48) with classes `FVaCuusUIVS/PS`, `FVaCuusCompositePS` (`VaCuusUIShaders.h:26-59`). A repo-wide grep for blur/backdrop in `VaCuusRender` + `Shaders` finds only comments; the `m1-render-spike` branch's tree likewise contains only `VaCuusUI.usf` (git ls-tree). The "ported GL3 blur chain" is **spec future work** ("UE global shaders ported from RmlUi's reference GL3 backend … blur chain for filter/box-shadow/backdrop", spec :160-162), with the reference vendored at `ThirdParty/RmlUi/Backends/RmlUi_Renderer_GL3.cpp`: `RenderBlur(sigma, source_destination, temp, …)` (:1351), downscale-first for large sigma (:1362), direction/texel-offset separable passes (:1406-1407), the 1px-transparent-border upscale trick (:1422-1423), used by both `filter: blur` and drop-shadow (:1794, :1822). The engine's own `SlatePostProcessor.cpp:757-832` (downsample → gaussian or Dual-Kawase → upsample **with CornerRadius support**) is the closer structural template but lives in the module's Private folder, so it must be mimicked, not linked. Yes — a separable gaussian at half-res over the scene region is exactly the engine's own scheme; what's missing is *everything*: downsample pass, blur PS pair, glass-mask composite PS, and a pooled half-res RT.

## 4. How backdrop-filter reaches the RenderInterface, and the recorder's exact gap

Vendored `Include/RmlUi/Core/RenderInterface.h` — 21 virtuals. The recorder implements **9** (`VaCuusRecordingRenderInterface.h:109-117`): CompileGeometry(:40), RenderGeometry(:45), ReleaseGeometry(:48), LoadTexture(:54), GenerateTexture(:59), ReleaseTexture(:62), EnableScissorRegion(:66), SetScissorRegion(:70), SetTransform(:93). **At silent-no-op defaults, 12** (`RenderInterface.cpp:20-63`): EnableClipMask(:78), RenderToClipMask(:86), PushLayer(:98), CompositeLayers(:105), PopLayer(:107), SaveLayerAsTexture(:112), SaveLayerAsMaskImage(:116), CompileFilter(:122), ReleaseFilter(:125), CompileShader(:131), RenderShader(:137), ReleaseShader(:140).

The backdrop path (`Source/Core/ElementEffects.cpp`, Enter stage :247-281) issues, for a root-level glass panel:

1. `backdrop_source_layer = GetTopLayer()` (:249) — the render stack is empty at document root (asserted empty at frame start, `RenderManager.cpp:50`), so this is `LayerHandle 0`, **the reserved base layer** (`RenderManager.cpp:317-319`; `RenderInterface.h:96`). **RmlUi's "backdrop" is its own base layer — it has no concept of the 3D scene.** For VaCuus the base layer is the per-view RT, transparent wherever UI hasn't drawn; the scene must be *injected under it* by us. This is the pivotal semantic fact of the whole feature.
2. Scissor = border box extended by ink overflow, 3σ for blur (`ElementEffects.cpp:236-245, 265`; `FilterBlur::ExtendInkOverflow`, `FilterBlur.cpp:22-27`).
3. `PushLayer()` → temp (:266-267); `CompositeLayers(0, temp, Blend, [blur])` (:269-274).
4. Clip to the element's border box — **border-radius always goes through the clip mask** (`ElementUtilities.cpp:157-168`: `if (has_border_radius || (transform && has_clipping_content))` push clip-mask geometry; applied via `SetClipMask`, :222-230); square corners use scissor only (:178-186, 224-228).
5. `CompositeLayers(temp, 0, Blend, {})` (:278), `PopLayer()` (:279), scissor restored (:280).

Filter compile: `FilterBlur::CompileFilter` → `CompileFilter("blur", {"sigma": resolved px})` (`FilterBlur.cpp:16-20`), only wrapped into a live handle if we return nonzero (`RenderManager.cpp:274-276`). Property registration: `StyleSheetSpecification.cpp:408`.

**Glass therefore needs 5 new virtuals** — CompileFilter/ReleaseFilter + PushLayer/CompositeLayers/PopLayer — **plus 2 for rounded glass** (EnableClipMask/RenderToClipMask). NOT needed: SaveLayerAsTexture/SaveLayerAsMaskImage (element `filter:`/mask, Exit stage :283-312) and the CompileShader trio (gradients/material decorators — separate M5 track). Buffer changes: new command types (PushLayer/PopLayer/CompositeLayers + filter list; ClipMask ops) and a new resource pair `NewFilters`/`ReleasedFilters` — `VaCuusCommandBuffer.h:191-241` already names this exact scenario: the member-count tripwires and `HasResourceTraffic()` **must** be extended, and the new command fields added to `FVaCuusCommandHashImage` (:261-269) or the idle gate silently withholds changed frames (:379-387).

## 5. The composite today, and where scene-sampling slots — the design correction

Today (`VaCuusSlateElement.cpp:54-141`): raw-RHI replay in a parameterless RDG pass (:70-84) → `RegisterExternalTexture(OutputRT)` (:106) → `FVaCuusCompositePS` premultiplied-over (`One, InvSrcAlpha`, :125-126) into `Inputs.OutputTexture` at `DestRect + ElementsOffset` (:110-140). The RT is `PF_B8G8R8A8`, premultiplied, SRV-state invariant (`VaCuusReplayRenderer.cpp:164-172`); replay draws with the same premultiplied blend (:242-243) inside one `BeginRenderPass` (:231-234, ends :356-358). DestRect comes from `SVaCuusWidget::OnPaint` (:278-286, `MakeCustom` at :286); buffers arrive via `VaCuusRmlDocumentHost.cpp:494`.

**The correction:** replay runs only when a buffer was published (`VaCuusSlateElement.cpp:56`), and the idle gate exists precisely so a static HUD publishes ~nothing (`VaCuusRecordingRenderInterface.h:99-101, 133-136`). The scene changes every frame regardless. Bake the blurred scene into `OutputRT` at replay time and an idle HUD shows a **frozen backdrop over a moving scene**. Two coherent designs:

- **(A) Composite-time glass — recommended for M5.** Replay does *not* execute the scene half of a layer-0 backdrop composite; instead the recorded sequence `{scissor, CompileFilter(blur,σ), CompositeLayers(0→temp→0), clip-mask geometry}` is distilled (either recorder-side into the buffer, or replay-side) into a **glass list** — region + rounded-rect params (or clip-mask geometry) + σ — stored on `FVaCuusSlateElement` beside `DestRect`, persisting across idle frames like the RT itself. Every engine frame, `Draw_RenderThread`: (1) one bilinear downsample pass sampling `Inputs.OutputTexture` at the glass regions into a pooled half-res RT (§2 — no copy pass); (2) separable blur ping-pong at half-res; (3) per glass region, draw the blurred texture into OutputTexture masked by the glass shape (SDF rounded-rect in the PS, `SrcAlpha/InvSrcAlpha` so the edge lerps blurred-over-sharp = correct AA; the engine's blur upsample with `CornerRadius` is the pattern, `SlatePostProcessor.cpp:822-832`); (4) the existing UI-RT composite on top, unchanged. Idle economy intact; backdrop live at engine rate. Documented v1 limitation (already the spec's scope — "for root-level elements", spec :193-194): the glass blurs the scene + lower-layer *Slate* content, not same-context UI drawn beneath the element; in-page UI-over-UI backdrop needs the full layer stack in the replayer (v1.x).
- **(B) Replay-time glass, gate bypassed:** full layer stack in the replayer, recorder flags scene-dependent buffers (a layer-0 backdrop composite) to force publish every frame, blurred scene fed into the raw replay pass via parameter-struct `AddPass` (`RenderGraphBuilder.h:203-221`). RmlUi-exact for arbitrary nesting, but kills the idle win for any glass document and requires retaining a re-playable buffer. Not for the demo.

**Exact new pieces (design A):** *Shaders* — `VaCuusBlur.usf` (separable gaussian PS, direction+texel-offset uniform, GL3 `RenderBlur`/engine `FSlatePostProcessBlurPS` as references) and `VaCuusGlassPS` (sample blurred RT, rounded-rect SDF mask), both paired with the engine's `FScreenPassVS` like the existing composite (`VaCuusUIShaders.h:42-47`). *Recorder* — CompileFilter/ReleaseFilter (record `{type=blur, sigma}`; nonzero handle so RmlUi keeps the filter live, `RenderManager.cpp:274-276`), PushLayer/PopLayer/CompositeLayers commands; EnableClipMask/RenderToClipMask for rounded glass. *Buffer* — new command types + `NewFilters`/`ReleasedFilters` + tripwire/hash updates (§4). *Element* — glass-list state (set per published buffer, used every frame), pooled half-res RT (persistent, external-registered), passes (1)-(3) inserted before the existing composite. *Replayer* — skips layer commands other than glass extraction in v1.

## 6. Gamma / PF_FloatRGBA

- The existing composite writes RmlUi's sRGB-encoded premultiplied colors **raw** into OutputTexture — "no gamma conversion in M1" (`VaCuusSlateElement.cpp:122-126`; `VaCuusUI.usf:37-48`) — while ordinary Slate batches apply shader gamma `DisplayGamma = engine 2.2` unless HDR (`SlateRHIRenderingPolicy.cpp:1508-1509`). This works because LDR OutputTexture holds display-encoded pixels.
- **Glass is gamma-neutral by construction:** it samples OutputTexture and writes back into the same texture — identical encoding in and out; it inherits M1's contract and adds no new gamma requirement. The blur runs on display-encoded values; that is exactly what the engine's own Slate blur does — no linearization anywhere in the blur path, the only gamma-named code there is HDR-composite CVars (`SlatePostProcessor.cpp:49-105`).
- `PF_FloatRGBA` arises via `r.DefaultBackBufferPixelFormat=3` (`RendererSettings.cpp:41-43`) or HDR output (`GRHIHDRDisplayOutputFormat`, `SlateRHIRenderer.cpp:760-766`); the desktop default is `PF_A2B10G10R10` (`SceneTextures.cpp:71-80`). In a linear float target the *tint/blur* remains self-consistent (same-texture in/out), but the UI RT's sRGB-encoded content mismatches — that is the **pre-existing** M1 composite gap the spec's planned FloatRGBA permutation addresses (spec :181-182), not a new glass liability. Under `bCompositeUIWithSceneHDR` the scene is absent from OutputTexture entirely (§1) — glass must detect-and-degrade (blur of UI-only content) → **LDR-only confirmed** (spec :23-24 already says LDR).
