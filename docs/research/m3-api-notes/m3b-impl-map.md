# M3a data-binding map — substrate for M3b (arrays + `data-for`)

Code root: `/w/Unreal/VcHost/Plugins/VaCuus/Source/` — all paths below are relative to it. Every cited line was opened and read.

## 1. The classifier, and where arrays/maps/sets/fixed arrays are refused

The classifier is `VaCuusModelLayoutPrivate::ClassifyProperty(const FProperty*, EVaCuusFieldKind&, const TCHAR*&)` — `VaCuus/Private/VaCuusModelLayout.cpp:173-332`, called from `FVaCuusModelLayout::BuildLevel` at `VaCuusModelLayout.cpp:603`. Ordering is documented as load-bearing ("Most-derived first, always", `VaCuusModelLayout.cpp:163-169`).

Refusals:

- **`FArrayProperty`** — `VaCuusModelLayout.cpp:291-295`:
  > `"TArray binding is M3b: a flat entry keyed on a byte offset cannot address an array element, whose address is FScriptArrayHelper::GetRawPtr(i) and is only valid for the current Num()"`
- **`FMapProperty`** — `VaCuusModelLayout.cpp:297-300` ("no RmlUi map view, and FMapProperty::Identical is O(n^2) via IsPermutation").
- **`FSetProperty`** — `VaCuusModelLayout.cpp:302-305`.
- **Fixed-size C arrays (`ArrayDim > 1`)** — refused *before* classification, in `BuildLevel`, `VaCuusModelLayout.cpp:499-506`: one `FProperty` with many values, "indexed binding is M3b". Comment at `:496-498`: "Binding element 0 and dropping the rest would be a silent partial bind."
- Related refusals that shape the type table: `FWeakObjectProperty` `:281-287`, hard `FObjectProperty` `:310-316`, other `FObjectPropertyBase` `:317-322`, delegates `:324-328`, generic fallback `:330-331`.

A second, runtime-side array refusal already exists in the adapter: `FVaCuusStructDefinition::Child` refuses an indexed address (`{{Origin[0]}}`) with a latched warning "arrays are M3b" — `VaCuus/Private/VaCuusDataVariable.cpp:316-334`.

## 3. `FVaCuusModelField::CopyValue`

`VaCuusModelLayout.cpp:51-58`: both pointers go `ContainerPtr(base)` (adds the flattening `ContainerOffset`) then `Property->ContainerPtrToValuePtr<void>(...)`, and the copy is **`Property->CopySingleValue(dest, src)`** — yes, `FProperty::CopySingleValue` on the field property. The header rationale (`VaCuusModelLayout.h:155-177`): CopySingleValue not memcpy because of bitfield masking, and:

> "Single, not Complete: FVaCuusModelLayout refuses ArrayDim > 1, so there is exactly one value per entry." (`VaCuusModelLayout.h:170-171`)

`CopyValue` is used identically by all four stages: sampler shadow store (`VaCuusModelSampler.cpp:243`), channel slot write (`VaCuusModelChannel.cpp:149`), UI-shadow apply (`VaCuusBoundModel.cpp:175`), and the sampler-cost test's rig applier (`Tests/VaCuusModelSamplerTest.cpp:550`).

## 4. The RmlUi adapter

All in `VaCuus/Private/VaCuusDataVariable.h/.cpp` (private header; RmlUi includes legal per `VaCuusDataVariable.h:11-15`). The door used is `BindCustomDataVariable` + a hand-rolled `VariableDefinition`, bypassing `Family<T>` entirely (`VaCuusDataVariable.h:27-45`).

- **`FVaCuusScalarDefinition final : public Rml::VariableDefinition`** (`VaCuusDataVariable.h:100-128`), constructed as `DataVariableType::Scalar` (`.cpp:44`). `Get` switches on kind (see #2); `Set` **always refuses** and counts `GNumRefusedSets` (`.cpp:220-245`) — M3a's one-way contract (I3).
- **`FVaCuusPropertyDefinition final : public Rml::BasePointerDefinition`** (`VaCuusDataVariable.h:140-150`): the *only* addressing step on the RmlUi path — `DereferencePointer` is `Property->ContainerPtrToValuePtr<void>(InContainerPtr)` (`.cpp:259-265`).
- **`FVaCuusStructDefinition final : public Rml::VariableDefinition`** (`VaCuusDataVariable.h:162-219`), `DataVariableType::Struct` (`.cpp:272`). Members are a flat array of `{Rml::String Segment, VariableDefinition*, int32 ContainerOffsetFromModelBase, bool bNested}` (`.h:182-195`), linear scan (`.cpp:303-314`). `Child` (`.cpp:316-377`) resolves by string; a leaf hit returns `Rml::DataVariable(Member->Definition, (uint8*)InModelBase + Member->ContainerOffsetFromModelBase)` (`.cpp:338`).
- **The pointer invariant** (`VaCuusDataVariable.h:60-69`): a struct definition is ALWAYS handed the **model base**, never a shifted pointer; a leaf's absolute-from-base offset is applied exactly once, when `Child()` hands out the property definition. Nested members carry offset 0 (`.cpp:296-300`, "there is no parameter to get it wrong with"). The header explicitly notes RmlUi's own `ArrayDefinition::Child` "computes a new [pointer]" (`.h:67-69`) — the pattern an array definition would follow instead.
- **`FVaCuusModelDefinitions`** (`.h:228-276`): every definition one model **TYPE** needs, built once, owning three `TArray<TUniquePtr<...>>` (pointee-stable, `.h:266-270`), plus `StructsByPrefix` and `TopLevelVariables`. Built by pass 1 (per-leaf) + pass 2 (per top-level name) at `.cpp:401-460`; `GetOrCreateStructFor` recursively builds struct levels by dotted prefix (`.cpp:462-491`).
- **`FVaCuusDefinitionRegistry`** (`.h:297-312`, `.cpp:504-562`): process-wide `TMap<const UScriptStruct*, TUniquePtr<FVaCuusModelDefinitions>>` static (`.cpp:29`), **UI thread only, asserted** (`.cpp:509`), keyed on the raw `UScriptStruct*` with the type pinned via `TStrongObjectPtr` so the key can't be reused (`.h:257-263`). Never cleared while the UI thread is up; released only in `FVaCuusUIThread::Exit()` via `ReleaseAll()` (`.cpp:536-562`; call site `VaCuus/Private/VaCuusUIThread.cpp:834-841`) to avoid at-exit static destruction touching GUObjectArray.
- **Per-model materialization**: definitions carry "no shadow pointer, no per-instance state at all" (`.h:281-284`); two views over the same USTRUCT share one set and "differ only in the void* they were bound with". `VaCuusData::BindModelVariables` (`.cpp:568-612`) type-checks the shadow against the layout (`:576-581`), fetches/creates definitions (`:584`), then **`Constructor.BindCustomDataVariable(name, Rml::DataVariable(Variable.Definition, Shadow.GetData()))`** per top-level name (`.cpp:596`) — every variable bound with the same pointer, the shadow base. Called from `FVaCuusBoundModel::BindToContext` (`VaCuus/Private/VaCuusBoundModel.cpp:100`), which creates the data model via `Context.CreateDataModel` (`:78`) and pre-converts `TopLevelNamesUtf8` once (`:105-109`; rationale `VaCuusBoundModel.h:224-231`).

## 5. The apply loop

- **Location in the UI frame**: `FVaCuusUIThread::RunFrame`, the `DataApply` perf scope — `VaCuus/Private/VaCuusUIThread.cpp:870-879`, marker comment `// (data snapshots: M3a)` at `:871`. Deliberately after both drains and before `Context::Update()` (`:873-876`), and deliberately **not** inside the `HasView()`-gated record loop (`:885-898` — sizeless UMG views must still get updates).
- `ApplyModelUpdates` (`VaCuusUIThread.cpp:908-927`) walks `Models` (`TMap<uint32, TArray<TSharedRef<FVaCuusBoundModel>>>`, `VaCuusUIThread.h:341`) and calls `ApplyPendingUpdate()` per model, gated on nothing.
- `FVaCuusBoundModel::ApplyPendingUpdate` (`VaCuusBoundModel.cpp:125-144`): no-op (and deliberately non-consuming) before `bBoundToContext` (`:129-138`), else `Channel.ConsumeUpdate([this](const FVaCuusModelUpdate& U){ ApplyUpdate(U); })`.

- **The echo**: folded into `FVaCuusModelChannel::ConsumeUpdate` (`VaCuus/Private/VaCuusModelChannel.cpp:172-207`) — generation guard against the no-op swap (`:192-195`), applier runs, then `AppliedGeneration.store(Update.Generation, std::memory_order_release)` **after** the apply (`:205`). ## 9. What will block or complicate arrays

1. **"Exactly one value per entry" is a stated invariant of `CopyValue`.** `VaCuusModelLayout.h:170-171`: "Single, not Complete: FVaCuusModelLayout refuses ArrayDim > 1, so there is exactly one value per entry." Four pipeline stages call `CopyValue` per dirty bit; for a `FArrayProperty` field, `Property->CopySingleValue` on the array value would copy the whole container. [inference] For `FArrayProperty` that is a deep copy that allocates/frees element storage — engine semantics are the other agent's job, but the *call shape* is fixed at `VaCuusModelLayout.cpp:56-57`.
2. **Flat byte-offset addressing cannot reach elements — the classifier says so itself.** `VaCuusModelLayout.cpp:293-294`: element addresses are `FScriptArrayHelper::GetRawPtr(i)`, "only valid for the current Num()". `FVaCuusModelField::ContainerOffset` is a build-time absolute offset (`VaCuusModelLayout.h:123-134`), and the adapter's core invariant — offset "applied exactly once, at the moment Child() hands out the property definition", struct definitions always handed the model base (`VaCuusDataVariable.h:60-66`) — cannot express a heap-resident element. The header already points at the pattern to use: "ArrayDefinition::Child computes a new [pointer] (DataVariable.h:143-163)" (`VaCuusDataVariable.h:67-69`). Also note both RmlUi array-ish types are `final` upstream ("StructDefinition and ArrayDefinition cannot be reused the same way: both are `final`", `VaCuusDataVariable.h:80-81`), so an array definition must be hand-rolled like the struct one was.
3. **Allocation-free publish claims a TArray copy breaks.** The channel is documented "latest-wins, allocation-free in the steady state" (`VaCuusModelChannel.h:49-50`); `PublishSet` is "kept as a member so a publish allocates nothing" (`VaCuusModelChannel.h:284-285`); slot buffers allocate "at most three times ever" (`VaCuusModelChannel.cpp:127-131`). A growing TArray field copied into a slot re-allocates inside `Publish`. Worse: the republish protocol rewrites **every outstanding field with its current value on every publish** (`VaCuusModelChannel.cpp:145-151`, "CURRENT VALUES, read now, for every bit in the set"), so during a UI stall an unacked array is deep-copied whole every game frame ("bounded by the number of distinct changed fields, never by how long the stall lasted", `VaCuusModelChannel.h:98-101` — for arrays, "a field" is no longer O(1)).
4. **The shadow's cost argument assumes per-model, not per-frame allocation.** `VaCuusModelShadow.h:36-38`: full-fidelity copy "is the price of the accessors, and it is paid once per model, not per frame." An array field pays per change (three slot instances + game shadow + UI shadow all hold real TArrays).
5. **Dirty granularity is one bit per field, checked.** `FVaCuusModelUpdate::DirtyFields` is "One bit per FVaCuusModelLayout field index" (`VaCuusModelChannel.h:41-42`), and `ApplyUpdate` `checkf`s `DirtyFields.Num() == Layout.GetFields().Num()` (`VaCuusBoundModel.cpp:154-156`). Bit counts are `Init`'d once in the channel constructor (`VaCuusModelChannel.cpp:17-19`) and `MarkEveryFieldDirty` deliberately "cannot resize" (`VaCuusModelChannel.cpp:38-39`). Arrays therefore get whole-array dirtiness (one bit) or a redesign of the bit space; per-element bits cannot be sized at layout-build time.
6. **Flattening cannot apply to arrays of structs.** The layout's shape is "one entry per bound leaf, nested structs flattened, no TFieldIterator afterwards" (`VaCuusModelLayout.h:205-207`); leaf count is fixed per type at build time, but an array's element count is per-instance. An `Array` kind must be a *leaf* whose element type is described separately — the flat `Fields`/`TopLevelNames`/bit-index machinery cannot enumerate elements.
7. **The diff budget path.** `SoftPathsDiffer` justifies avoiding two allocations per field per frame "on a path budgeted at 0.02 ms" (`VaCuusModelSampler.cpp:66-67`). An array compare is O(elements) per frame per field; the "compare what the UI ships" rule (`:83-84`) applied naively to a 200-row array of structs is 200×leaf comparisons every game frame even when idle. The cost fixture/measurement pattern in #7 is where that must be quantified.
8. **`StoreField` silently accepts new kinds** (`VaCuusModelSampler.cpp:228-244` — if-chain, falls through to `CopyValue`). For arrays containing FText, the Text projection (`:230-241`) would not run per element; nothing forces anyone to notice at compile time.
9. **Definitions must stay per-TYPE stateless.** The registry shares one definition set across all instances of a type; "a definition carries only an FProperty*, a field kind and a diagnostic string -- no shadow pointer, no per-instance state at all" (`VaCuusDataVariable.h:281-284`). An array definition's `Size()`/`Child()` must derive everything from the incoming `void*` at call time.
10. **Existing guardrails that turn into the M3b surface**: the struct `Child()` indexed-entry latch ("arrays are M3b", `VaCuusDataVariable.cpp:326-333`); the `.size` note — RmlUi handles `address.name == "size"` *inside* `ArrayDefinition::Child`, not in the core (`VaCuusDataVariable.cpp:347-350`), so the new array definition must implement it; the wire-name validator already reserves `it`/`it_index` (`VaCuusModelLayout.cpp:361-362`), protecting `data-for` iterator names; and `ValidateTopLevel` refuses a top-level property named `Size` (`VaCuusModelLayoutTestTypes.h:178-180` is the fixture for that).
11. **The one-way write refusal has a per-leaf shape.** Every leaf write funnels to `FVaCuusScalarDefinition::Set` "by shape" (`VaCuusDataVariable.cpp:227-231`); an array definition's own `Set`/element writes must preserve that funnel or I3 grows a hole.

Not settled from source (named experiments): whether `Rml::DataVariableType::Array` plus a custom `VariableDefinition` is sufficient for `data-for` on the `BindCustomDataVariable` path (requires reading `ThirdParty/RmlUi` `DataViewFor`/`DataVariable` sources, which I did not open — verify against the vendored tree before design); and the actual per-publish allocation cost of a 200-row array field (measure with the `Sampler.Cost` pattern extended with an array fixture, reporting idle/all-changed/one-element-changed).
